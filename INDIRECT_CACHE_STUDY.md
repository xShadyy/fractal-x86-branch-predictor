# Native Windows indirect target cache receiver (pilot I)

**Status:** the [31 October physical pilot](results/2026-10-31-windows-suite-pilot/README.md) built and measured I. Its held-out receiver and no-call controls passed, but its adjusted opposite-target hit changes were −0.6% and +0.2%, with intervals spanning zero. The linked PE review found separate target data-page loads and no apparent architectural opposite-line load; runtime corroboration and independent sessions are still needed. This is a user-mode Windows experiment and establishes no speculative-execution result.

## Scientific question

Ravichandran and Yan's [Fractal paper, §7.1](https://people.csail.mit.edu/mengjia/data/2026.SP.fractal.pdf) begins its indirect branch predictor work with a single-domain baseline: train a fixed indirect branch to one target, actually direct the probe to another target, and use a cache receiver to look for an effect associated with the trained target. They distinguish speculative *fetch* from *execution* using separate instruction-cache and data-cache receivers before studying privilege and address-space boundaries. Pilot I adapts only the **single-process, same-domain, data-cache receiver question** to Windows x64 on this host. Its intervention, physical branch targets, and cache lines are different from the Apple M1 work. It does not test Fractal's cross-domain findings or its operating system.

Question: after the same indirect JMP is trained to target `t`, does an architectural one-call probe to target `p` leave the *other* target's distinct data line unusually likely to be hot when `t != p`, relative to target-matched training and controls? The measured outcome is reload time of the nonarchitectural target's data line; the paired contrast is the difference in thresholded hit fractions. This pilot does not have a validated instruction-cache fetch receiver and cannot distinguish all sources of a data-cache hit without inspecting the physical executable.

## Fixed protocol

- One MASM `indirect_cache_site` loads a pointer from a dedicated 4096-byte-aligned slot and executes `jmp rax`. Target zero reads the first byte of `data_zero` and returns `1`; target one reads `data_one` and returns `2`. The data arrays and pointer slot are separately 4096-byte aligned. The target bodies are separated by at least 128 bytes of code padding. The C program checks architectural sums and logs target and data addresses.
- Each episode begins with 128 repetitions of a `0011` prelude through the same dispatch site. This standardizes prior activity; it is **not** asserted to reset a predictor or path-history register. Real training uses 256 identical target labels `0` or `1`. Fixed training uses a 256-element `0011` stream. Both use the **same noinline C feeder loop** and MASM site; sham training reads an input with a separate branchless MASM function.
- The program selects the architectural probe target `p`, flushes **both** data lines and the pointer slot, and issues an `mfence`. Its single shared-site probe targets `p`; it never intentionally calls the other target in a primary cell. It times a reload of the other data line with `lfence; rdtsc; lfence`, a load, then `lfence; rdtsc`. A separate skip condition omits the probe call after an otherwise identical preparation.
- The factorial intervention has 12 cells: real, fixed, or sham training × `t ∈ {0,1}` × `p ∈ {0,1}`. Four architectural positive/negative controls directly call the opposite or matched target at the **same site** for both receiver lines. Two fixed-training no-call controls and four train-matched real no-call controls test residual heating, prefetch, and harness effects following the flush. These sum to **22 cells**.
- A nonzero 32-bit seed selects a Fisher–Yates permutation for every 22-block cycle, then each condition takes every within-block position by rotation. There are 22 warmup blocks and 220 recorded complete blocks, each with 64 raw reload times per cell. The process pins itself to one allowed logical CPU and records `CPUID` vendor/signature, TSC, `CLFLUSH`, hypervisor bit, logical CPU affinity, Windows build, full schedule hash, checksum, and architectural sink. A Windows build refuses to proceed if invariant TSC, 64-byte `CLFLUSH`, or affinity are unavailable.

For architectural target `p`, define `H(a,t,p,b)` as the fraction of 64 reloads labeled hit in complete block `b`, with trainer arm `a` and training label `t`. The primary contrast `D_a(p)` averages `H(a,1-p,p,b) - H(a,p,p,b)` across the blocks. The predeclared secondary contrasts are `D_real(p) - D_fixed(p)` and `D_real(p) - D_sham(p)`, separately for `p=0` and `p=1`. A positive association in both probe directions with cold train-matched skips would motivate follow-up; it would not alone prove wrong-path execution.

The analyzer learns **separate thresholds for the two receiver lines** using only the first 110 blocks' hot/cold controls. It reports held-out hit fractions from blocks 110–219. `--strict` passes only if, for **each** receiver line, the held-out architectural hot rate is at least 95%, and cold, fixed no-call, and both train-matched real no-call rates are each at most 5%. It reports all predeclared contrasts whether gates pass or fail, with within-run bootstrap intervals resampling complete **22-block position cycles** (10 cycles), not treating 64 episodes as independent host replications. The first 110 blocks train only the threshold; paired contrasts use all 220 blocks. A null or failed gate is preserved as a result, never converted to a positive claim.

## Run and audit

In VS Code on the Windows host, run the **Indirect target cache receiver: build, run, analyze (Windows)** task if available, or in the integrated PowerShell terminal:

```powershell
./scripts/check_indirect_cache_windows.ps1 -Seed 1732072136
```

The seed is an example; choose a new, precommitted nonzero 32-bit value for each independently planned run. Omitting `-Seed` generates and prints a seed *before* building. The script archives a timestamped `.exe`, raw `.log`, `.build.json` with source/tool/binary hashes and Git state, `.build.log`, and a `.disasm.txt` when `dumpbin.exe` is present. The `.exe` and `.log` are paired by timestamp and recorded binary SHA-256; retain both and the build sidecars. The script calls the strict Python analyzer and marks the provenance status `statistically_validated_instruction_audit_pending` only if trace and receiver gates pass. That status is **not** an instruction audit or speculative execution finding.

Before interpreting any receiver association, inspect the disassembly of the **archived executable** (not merely the `.asm` source): verify exactly one physical indirect JMP site and shared feeder call path; the real/fixed/prelude pointer stores feed the same instruction; target zero reads only `data_zero` and target one only `data_one`; code lines are actually distinct; the pointer slot is flushed after selecting `p`; neither C setup nor calibration nor compiler-emitted code architecturally loads the opposite line between the flush and timed reload; no unexpected fence blocks the intended path; and the timer keeps the intended load inside its interval. Preserve the audit notes together with the exact binary hash. A source-level assertion or all-green analyzer cannot replace this inspection.

Even with a verified binary and passing controls, repeat with independent seeds and separate host sessions and review raw tails, medians, temporal drift, hypervisor activity, and target-direction asymmetry. A Windows process cannot control interrupts and scheduling as Fractal does; host hypervisor presence is recorded, and timer quantization and asynchronous work can affect a cache receiver. The no-call controls reduce a specific train-dependent heating confound but do not exclude all speculative or non-speculative alternate causes. Report results as **an exploratory same-domain cache association** until stronger physical controls and independent replication justify a narrower claim. An absent effect on this setup does not establish the absence of an indirect branch predictor.
