# Full native Windows branch research pilot

**Status:** source package prepared after the archived A/B two-day series. One session runs four baseline checks and seven exploratory studies. This is the **first physical pilot** of B2/C/D/E/F/H/I, not a report of their measured effects. Their optimized Windows executables and first traces still require compilation, validation and instruction audit on the Ryzen host. Keep every attempted build and run, including failures and null effects.

## Why these studies form one suite

The [Fractal paper](https://people.csail.mit.edu/mengjia/data/2026.SP.fractal.pdf) motivates controlled instruction locations, deliberate branch histories, and a train-then-receiver sequence. Its Apple M1 experiments cross privilege and address-space domains. These native x86 Windows tests stay within one user-mode process; most measure TSC latency, while I measures a target-specific cache-reload channel. The session first rechecks the cache and architectural receiver controls plus archived A/B questions, then runs seven exploratory studies. The [stage map](WINDOWS_RESEARCH_PROGRAM.md) states which paper questions these measurements can and cannot address.

## B2: one call, sixteen calls, and a same-site trainer

The complete [B2 design](EXPLORATORY_HISTORY_B2.md) specifies 36 conditions: three trainer arms (`real`, same-site `fixed`, separate-site branchless `sham`) × two train labels × two probe outcomes × two probe lengths, plus fast, small-added-work, and `PAUSE` timer controls for each probe outcome and length. The design has 36 warm-up and 720 recorded complete blocks, 128 episodes per condition, and 20 position-balanced 36-block cycles. Its 3,317,760 recorded episodes entail 1,726,894,080 prelude/training/probe calls. The actual runtime is unknown until the Windows pilot.

For `p=0`, mismatch is training label 1 minus label 0; for `p=1`, mismatch is label 0 minus label 1. Within each complete block and length, form `D_arm(p,n)` from the corresponding difference of two 128-episode totals, divided by 128. The four exploratory main outcomes are `F(p,n)=D_real(p,n)-D_fixed(p,n)` for `p∈{0,1}`, `n∈{1,16}`. Report the four `S(p,n)=D_real(p,n)-D_sham(p,n)` as secondary comparisons, plus each component. Report the length interaction `F(p,1)-F(p,16)` **within blocks before trimming**. A small total effect at `n=16` cannot automatically be divided by 16 to infer that the first call was diluted; the 16 calls also modify subsequent state and loop cost.

The B2 timer controls cover all four `(p,n)` combinations. The separate small-work timer aims to show sensitivity near the few-tick scale; its exact optimized instructions and measured size must be audited, rather than assumed from C source. The same-site fixed trainer is an imperfect but closer comparison than sham because it executes the conditional instruction with fixed decisions while reading the same live train bytes. Its own mismatch-minus-match interval is checked against the stated ±1 tick per probe practical tolerance. Full conditions, control gates and limitations are in the linked B2 design.

## C: balanced run-length pattern sweep

Each of the six 8,192-byte inputs is balanced with 4,096 zeros and 4,096 ones. The five periodic inputs repeat `01`, `0011`, `00001111`, `0000000011111111`, or sixteen zeros followed by sixteen ones. The sixth is a freshly generated balanced shuffle in each block. The primary branch path always calls the **same conditional instruction** and reads the live bytes; its runtime mode chooses whether decisions follow live bytes or the fixed `0011` stream. A separate branchless path also reads the live bytes. Thus the fixed and branchless modes detect timing changes from input handling or the mode baseline that need not reflect the branch's live decisions.

There are 18 pattern/mode conditions plus a fast/slow timer pair, 20 warm-up blocks, and 400 recorded complete blocks. A seed-derived shuffled order is rotated across each 20-block cycle, giving 20 complete position cycles. The recorded condition batches contain 65,536,000 timed loop iterations in total. The preselected exploratory anchor is the **within-block** adjusted period-2 versus period-32 difference:

```text
C_primary = [(live_period2 - live_period32)
           - (fixed_period2 - fixed_period32)] / 8192
```

Report the adjusted comparisons of periods 2, 4, 8, 16 and shuffle against period 32, plus shuffle versus period 4 as the earlier A reference. Include the unadjusted live/fixed/branchless components and timer control, with units in TSC ticks per iteration. For the primary period-2-minus-period-32 contrast, the *entire* fixed and branchless within-run intervals must each fit inside ±0.5 tick per iteration, and the timer must have a positive interval lower bound and at least 95% positive blocks before treating the contrast as control-supported. Secondary contrasts have no suite acceptance gate, but interpreting any one of them as decision-order-sensitive requires its corresponding fixed and branchless controls to be negligible on the stated scale. These multiple exploratory contrasts describe a response profile; one apparently nonzero point among them is not proof of a mechanism or an estimate of predictor capacity. Period changes also change transition frequency, so this is not a pure entropy manipulation. There is no prelude that proves predictor state has reset between conditions; counterbalanced position and long batches reduce but cannot eliminate carryover. The earlier A shuffle-versus-`0011` observation is a known reference, not a new discovery from C, and it cannot be numerically pooled with C because code address and measurement protocol differ.

## D: position of balanced intervening branches

Each episode has a common 256-call balanced prelude at the target site, 256 balanced filler calls split around a 256-call all-`t` training phase, then one fixed-outcome timed call to the target site. The post-training share of filler is `L∈{0,16,64,256}`; the other `256-L` filler calls occur before training. The same-site trainer executes either live all-`t` decisions or a fixed `0011` decision stream while reading the same all-`t` live bytes. This retains the total count of filler and training calls while varying the position of balanced activity relative to training. It does **not** isolate a hardware history length: the change also alters pre-training context and cannot erase unobserved system activity.

The main matrix is two trainer arms × two train labels × two probe outcomes × four filler positions = 32 conditions. Fast, small-added-work and `PAUSE` timer controls at `L=0` and `L=256` for both probe outcomes add 12, giving 44 conditions. With 44 warm-up and 704 recorded complete blocks at 128 episodes per condition, there are 16 position-balanced cycles and 3,964,928 recorded episodes. The recorded schedule entails approximately 3,049,029,632 prelude/filler/training/probe site calls, subject to verification in the physical code audit. Its runtime is unknown before the Windows pilot.

At each `L`, form mismatch-minus-match differences from each trainer's two 128-episode totals inside each complete block, then subtract the fixed-trainer difference from the real-trainer difference: `F_D(p,L)=D_real(p,L)-D_fixed(p,L)`. Report both probe outcomes at all four positions. Form the exploratory paired change `F_D(p,L)-F_D(p,0)` **inside each block** for `L=16,64,256`. A positive or vanishing contrast after filler would show sensitivity to this *specified sequence*, not a direct readout of predictor reset, retention depth, or cross-domain behavior. The small timer controls at both endpoint positions are critical before interpreting differences of a few ticks; intermediate positions remain diagnostic. The fixed trainer's own mismatch-minus-match interval is tested against ±1 tick per probe before describing it as negligible.

## E: fixed-budget training exposure

The E design holds the total training budget at 256 calls while varying the length of its immediately preceding all-equal suffix over `0, 4, 16, 64, 256`. The remainder is a fixed-decision prefix. Real and fixed-decision trainer arms, both training labels and both one-call probe outcomes form 40 main conditions; 12 endpoint timer controls bring the randomized complete block to 52 conditions. There are 52 warm-up and 1,040 recorded blocks, 64 episodes per condition and 20 position-balanced 52-block cycles. Compare each real-minus-fixed mismatch contrast to its own dose-zero contrast **within each block**, and retain both outcomes and all five dose levels. The dose-zero contrast is a structural null check. Moving the prefix/suffix boundary also changes immediate history, so a response curve does not identify a predictor counter or history-register length. The first host run must verify timer scale, fixed-arm neutrality and the actual instruction sequence.

## F: within-process virtual-address sensitivity

The F design copies one verified conditional-branch template into three executable locations: the receiver site, a site 4,096 bytes away with the same page offset, and a further site 128 bytes away with a different offset. Each one-call probe executes at the common receiver; the training site and its **entire call path** vary. The matrix has 34 conditions, 34 warm-up and 680 recorded complete blocks, 128 episodes per condition and 20 position-balanced 34-block cycles. Compare real and same-site fixed training separately for both probe outcomes, then compute paired between-site interactions inside complete blocks; retain sham and timer controls. Audit copied instruction bytes, recorded virtual addresses, executable permissions and the physical call sequence. A difference is evidence of sensitivity to this implemented address and call-path arrangement. It cannot identify a predictor index bit, predictor-table alias, ASID effect or cross-process sharing.

## H: indirect-target timing baseline

The [H design](INDIRECT_TARGET_STUDY.md) times a single indirect-jump dispatch after real, fixed and branchless-sham target training, separately for both possible target outcomes. Its 18 conditions include timer controls at each target. There are 18 warm-up and 360 recorded complete blocks, 128 episodes per condition and 20 position-balanced 18-block cycles. Report fixed- and sham-adjusted mismatch contrasts, component latencies, small and coarse timer controls and both target outcomes. This is a **whole-probe TSC latency baseline** for indirect target history; it has no target-specific transient receiver and cannot show speculative target fetch or execution.

## I: indirect-target cache-reload receiver

The [I design](INDIRECT_CACHE_STUDY.md) uses one indirect jump site for prelude, real/fixed training and probe. Two distinct targets load separate data lines and return distinct architectural values. After training, the runner sets the architecturally selected target, flushes both data lines **and the pointer slot**, invokes the site once, and times reloading the line for the **other** target. The 12 real/fixed/sham train-label × architectural-target conditions, four hot/cold controls, two fixed-training no-probe controls and four real-training train-matched no-probe controls give 22 conditions per block. There are 22 warm-up and 220 recorded complete blocks, 64 episodes per condition and ten position-balanced 22-block cycles. Calibrate the hit threshold using the first half's hot/cold controls, then check hot/cold and both no-probe families on the held-out half; retain both architectural-target outcomes and the real-minus-fixed and real-minus-sham comparisons. Its unit is cache reload TSC ticks with a calibrated hit classification, **not** H's whole-indirect-probe latency. A positive opposite-target hit association alone cannot prove speculative fetch or execution: verify the exact linked PE, addresses, target exclusivity, absence of architectural opposite-line access and control sensitivity on independent physical sessions before drawing a conditional transient interpretation. This remains a same-process user-mode test.

## Shared analysis, controls and provenance

1. Select and print an independent nonzero seed **before** each build and run. Each run must have a complete position-balanced schedule and a verifiable trace with raw condition totals, block/position/condition labels, architectural output checksums, CPU signature, affinity, hypervisor bit, Windows build, timestamps, exact EXE SHA-256 and schedule hash. Record Git HEAD/dirty status, exact `cl`/`ml64`/linker versions and flags, and source/analyzer hashes. Archive even inconclusive or failed attempts.
2. Check the **physical optimized Windows EXEs**, not just source, for the intended branch bytes, shared call sites, runtime decision selection, timed fences and separate timer wrappers. Relocations/ASLR require comparing trace addresses with PE RVAs. Linux source-level tests cannot substitute for the first physical instruction audit.
3. Form paired condition differences **inside each complete block**. The B2/C/D/E/F/H timing analyzers apply their declared trimmed estimates and resample complete position cycles for within-run 95% intervals; I calibrates a hit threshold on the first half of each receiver's hot/cold data, checks architectural controls on the held-out half, and reports paired within-block hit-rate contrasts. Report controls, exact samples and all planned outcomes. Within-run intervals do not represent machine-to-machine or day-to-day uncertainty. C reports ticks/iteration; B2/D/E/F/H report ticks per probe episode; I reports raw cache reload ticks and hit rates. Cache and speculation-receiver baselines have different endpoints. Never pool these as one effect size.
4. Timer controls show that the specific added work is detectable under their respective wrappers. A large `PAUSE` effect alone does not certify sensitivity to a 2-tick primary contrast. For B2 and D, an audited small-work control has a positive interval lower bound, an upper bound below +8 ticks per probe and a point estimate between +1 and +8, in each tested outcome/length or endpoint context. The coarse `PAUSE` control needs at least 95% positive paired blocks and a positive interval lower bound. E/F/H have their own declared small-work and fixed-trainer gates. E additionally tests dose zero; F additionally checks byte-identical copied branch templates and actual virtual addresses. I's held-out receiver gate requires each target's hot hit rate at least 95% and cold and no-probe hit rates at most 5%; this is a measurement-quality gate, **not** a transient-execution gate. For C, fixed-decision and branchless pattern controls and the separate timer must be inspected against its analyzer's declared tolerances. A failed control narrows interpretation rather than justifying deletion of the trace.
5. First perform **one complete pilot session** with four baseline checks and all seven exploratory studies, with a host snapshot and paired timestamped EXE/log for each completed run. Validate traces and binaries, record runtime and failures, then inspect disassembly and controls, especially the target-exclusive load path in I. The pilot is not a replication. Only afterward decide if unchanged code and adequate sensitivity justify a predeclared follow-up series with distinct seeds and days. Keep the original A/B archive and the new session distinct in any report.

No bootable operating system, custom driver, kernel mode or hardware profiler is required to run this suite. The scientific deliverable is a complete, reproducible local x86 characterization with explicit limitations, not an assertion that these programs reproduce Fractal's Apple M1 privilege-boundary result.

## One VS Code pilot task

After importing the bundle into the **existing repository**, open the repository folder in VS Code and choose **Terminal → Run Task → Full branch research pilot: baseline and seven studies (Windows)**. The task takes one host snapshot, runs cache controls, the existing speculative-cache receiver check, A and B1, then builds, runs and strictly analyzes B2, C, D, E, F, H and I with independent seeds in a preselected order. `scripts/run_suite_windows.ps1` writes its planned order and every run's status to a timestamped `out/suite-*/session.json`, with a transcript, trace and matching EXE for each completed study. A failed build, run or strict check is recorded and the independent planned studies continue; the suite returns a nonzero status at the end if any study did not pass. Keep every session entry and error transcript for review. Do not label a failed study as a validated physical measurement. The runtime is unknown until the host pilot and may be substantial.

Run **Terminal → Run Task → Exploratory suite: package latest evidence ZIP (Windows)** after the pilot. This creates one `out/suite-evidence-*.zip` with the session record, host snapshot, all available timestamped trace/EXE pairs, build provenance, disassemblies, and transcripts, including failed attempts. Review the host snapshot for hardware details before sharing the ZIP. The first physical run is a **pilot**. Do not invoke the suite's follow-up mode until its physical binaries, timer controls and trace results have been reviewed and any protocol corrections versioned.

Once the pilot is audited, the same imported code can run a follow-up without another merge: from the repository root in PowerShell, use `./scripts/run_suite_windows.ps1 -Phase Followup -Rounds 7`. The runner accepts `-Rounds 1` through `-Rounds 7`; **seven rounds** rotate the seven exploratory studies so each occupies every study position once. Four baselines run at the start of each session, followed by seven exploratory runs in each round. New independent seeds are printed and recorded before builds. Seven rounds may take a substantial amount of time; measure actual pilot runtime before scheduling them. Optional `-LogicalCpu N` requests one host logical CPU for the session; verify the requested affinity against each exploratory trace's recorded CPU/affinity fields before using the runs as controlled same-CPU evidence. Different dates are separate sessions. Package each session with `./scripts/package_suite_windows.ps1`. Do not treat all randomized blocks in one session as independent day-level replications. The optional same-process cross-thread handoff study G is **not** implemented: uncontrolled Windows scheduling would make its current treatment uninterpretable.
