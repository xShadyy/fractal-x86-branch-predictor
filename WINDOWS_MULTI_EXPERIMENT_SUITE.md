## Why these studies form one suite

The [Fractal paper](https://people.csail.mit.edu/mengjia/data/2026.SP.fractal.pdf) motivates controlled instruction locations, deliberate branch histories, and a train-then-receiver sequence. Its Apple M1 experiments cross privilege and address-space domains and distinguish target fetch from target execution using separate cache channels. These native x86 Windows tests stay within one user-mode process; most measure TSC latency, while I measures a candidate target-specific data-cache channel. The session first reruns six existing cache and branch diagnostics, then eight exploratory studies. The [stage map](WINDOWS_RESEARCH_PROGRAM.md) and [paper claim matrix](PAPER_CLAIM_MATRIX.md) state which questions these measurements can and cannot address.

| **Balanced branch batch** | Repeat the seeded random versus periodic balanced-input batch and its branchless, no-load and timer controls. | Compare descriptively with the [archived physical baseline](results/2026-10-30-windows-v2-pilot/README.md); the ablation's branch sites differ, and timing does not count mispredictions. |

Treat a new trace as a diagnostic, not a definitive null test of prediction. |

## B2: one call, sixteen calls, and a same-site trainer

The complete [B2 design](EXPLORATORY_HISTORY_B2.md) specifies 36 conditions: three trainer arms (`real`, same-site `fixed`, separate-site branchless `sham`) × two train labels × two probe outcomes × two probe lengths, plus fast, small-added-work, and `PAUSE` timer controls for each probe outcome and length. The design has 36 warm-up and 720 recorded complete blocks, 128 episodes per condition, and 20 position-balanced 36-block cycles. Its 3,317,760 recorded episodes entail 1,726,894,080 prelude/training/probe calls. The [physical pilot](results/2026-10-31-windows-suite-pilot/README.md) completed this work but failed the one-call probe-1 small-work magnitude gate; its probe-0 one-call association remains exploratory.

For `p=0`, mismatch is training label 1 minus label 0; for `p=1`, mismatch is label 0 minus label 1. Within each complete block and length, form `D_arm(p,n)` from the corresponding difference of two 128-episode totals, divided by 128. The four exploratory main outcomes are `F(p,n)=D_real(p,n)-D_fixed(p,n)` for `p∈{0,1}`, `n∈{1,16}`. Report the four `S(p,n)=D_real(p,n)-D_sham(p,n)` as secondary comparisons, plus each component. Report the length interaction `F(p,1)-F(p,16)` **within blocks before trimming**. A small total effect at `n=16` cannot automatically be divided by 16 to infer that the first call was diluted; the 16 calls also modify subsequent state and loop cost.

The B2 timer controls cover all four `(p,n)` combinations. The separate small-work timer aims to show sensitivity near the few-tick scale; its exact optimized instructions and measured size must be audited, rather than assumed from C source. The same-site fixed trainer is an imperfect but closer comparison than sham because it executes the conditional instruction with fixed decisions while reading the same live train bytes. Its own mismatch-minus-match interval is checked against the stated ±1 tick per probe practical tolerance. Full conditions, control gates and limitations are in the linked B2 design.

## C: balanced run-length pattern sweep

Each of the six 8,192-byte inputs is balanced with 4,096 zeros and 4,096 ones. The five periodic inputs repeat `01`, `0011`, `00001111`, `0000000011111111`, or sixteen zeros followed by sixteen ones. The sixth is a freshly generated balanced shuffle in each block. The primary branch path always calls the **same conditional instruction** and reads the live bytes; its runtime mode chooses whether decisions follow live bytes or the fixed `0011` stream. A separate branchless path also reads the live bytes. Thus the fixed and branchless modes detect timing changes from input handling or the mode baseline that need not reflect the branch's live decisions.

There are 18 pattern/mode conditions plus a fast/slow timer pair, 20 warm-up blocks, and 400 recorded complete blocks. A seed-derived shuffled order is rotated across each 20-block cycle, giving 20 complete position cycles. The recorded condition batches contain 65,536,000 timed loop iterations in total. The preselected exploratory anchor is the **within-block** adjusted period-2 versus period-32 difference:

```text
C_primary = [(live_period2 - live_period32)
           - (fixed_period2 - fixed_period32)] / 8192
```

Report the adjusted comparisons of periods 2, 4, 8, 16 and shuffle against period 32, plus shuffle versus period 4 as the earlier A reference. Include the unadjusted live/fixed/branchless components and timer control, with units in TSC ticks per iteration. For the primary period-2-minus-period-32 contrast, the *entire* fixed and branchless within-run intervals must each fit inside ±0.5 tick per iteration, and the timer must have a positive interval lower bound and at least 95% positive blocks before treating the contrast as control-supported. Secondary contrasts have no suite acceptance gate, but interpreting any one of them as decision-order-sensitive requires its corresponding fixed and branchless controls to be negligible on the stated scale. These multiple exploratory contrasts describe a response profile; one apparently nonzero point among them is not proof of a mechanism or an estimate of predictor capacity. Period changes also change transition frequency, so this is not a pure entropy manipulation. There is no prelude that proves predictor state has reset between conditions; counterbalanced position and long batches reduce but cannot eliminate carryover. The earlier A shuffle-versus-`0011` observation is a known reference, not a new discovery from C, and it cannot be numerically pooled with C because code address and measurement protocol differ.

## D: position of balanced intervening branches

Each episode has a common 256-call balanced prelude at the target site, 256 balanced filler calls split around a 256-call all-`t` training phase, then one fixed-outcome timed call to the target site. The post-training share of filler is `L∈{0,16,64,256}`; the other `256-L` filler calls occur before training. The same-site trainer executes either live all-`t` decisions or a fixed `0011` decision stream while reading the same all-`t` live bytes. This retains the total count of filler and training calls while varying the position of balanced activity relative to training. It does **not** isolate a hardware history length: the change also alters pre-training context and cannot erase unobserved system activity.

The main matrix is two trainer arms × two train labels × two probe outcomes × four filler positions = 32 conditions. Fast, small-added-work and `PAUSE` timer controls at `L=0` and `L=256` for both probe outcomes add 12, giving 44 conditions. With 44 warm-up and 704 recorded complete blocks at 128 episodes per condition, there are 16 position-balanced cycles and 3,964,928 recorded episodes. The recorded schedule entails approximately 3,049,029,632 prelude/filler/training/probe site calls. The [physical pilot](results/2026-10-31-windows-suite-pilot/README.md) accepted D's sensitivity and fixed controls; its tested filler contrasts included zero and did not identify predictor retention depth.

At each `L`, form mismatch-minus-match differences from each trainer's two 128-episode totals inside each complete block, then subtract the fixed-trainer difference from the real-trainer difference: `F_D(p,L)=D_real(p,L)-D_fixed(p,L)`. Report both probe outcomes at all four positions. Form the exploratory paired change `F_D(p,L)-F_D(p,0)` **inside each block** for `L=16,64,256`. A positive or vanishing contrast after filler would show sensitivity to this *specified sequence*, not a direct readout of predictor reset, retention depth, or cross-domain behavior. The small timer controls at both endpoint positions are critical before interpreting differences of a few ticks; intermediate positions remain diagnostic. The fixed trainer's own mismatch-minus-match interval is tested against ±1 tick per probe before describing it as negligible.

## E: fixed-budget training exposure

The E design holds the total training budget at 256 calls while varying the length of its immediately preceding all-equal suffix over `0, 4, 16, 64, 256`. The remainder is a fixed-decision prefix. Real and fixed-decision trainer arms, both training labels and both one-call probe outcomes form 40 main conditions; 12 endpoint timer controls bring the randomized complete block to 52 conditions. There are 52 warm-up and 1,040 recorded blocks, 64 episodes per condition and 20 position-balanced 52-block cycles. Compare each real-minus-fixed mismatch contrast to its own dose-zero contrast **within each block**, and retain both outcomes and all five dose levels. The dose-zero contrast is a structural null check. Moving the prefix/suffix boundary also changes immediate history, so a response curve does not identify a predictor counter or history-register length. The [first host run](results/2026-10-31-windows-suite-pilot/README.md) retained a valid trace but failed two probe-0 small-work magnitude gates, several fixed-trainer equivalence gates and both dose-zero equivalence gates. Its dose response is inconclusive.

## F: within-process virtual-address sensitivity

The F design copies one verified conditional-branch template into three executable locations: the receiver site, a site 4,096 bytes away with the same page offset, and a further site 128 bytes away with a different offset. Each one-call probe executes at the common receiver; the training site and its **entire call path** vary. The matrix has 34 conditions, 34 warm-up and 680 recorded complete blocks, 128 episodes per condition and 20 position-balanced 34-block cycles. Compare real and same-site fixed training separately for both probe outcomes, then compute paired between-site interactions inside complete blocks; retain sham and timer controls. Audit copied instruction bytes, recorded virtual addresses, executable permissions and the physical call sequence. A difference is evidence of sensitivity to this implemented address and call-path arrangement. It cannot identify a predictor index bit, predictor-table alias, ASID effect or cross-process sharing.

## H: indirect-target timing baseline

The [H design](INDIRECT_TARGET_STUDY.md) times a single indirect-jump dispatch after real, fixed and branchless-sham target training, separately for both possible target outcomes. Its 18 conditions include timer controls at each target. There are 18 warm-up and 360 recorded complete blocks, 128 episodes per condition and 20 position-balanced 18-block cycles. Report fixed- and sham-adjusted mismatch contrasts, component latencies, small and coarse timer controls and both target outcomes. This is a **whole-probe TSC latency baseline** for indirect target history; it has no target-specific transient receiver and cannot show speculative target fetch or execution.

## I: indirect-target cache-reload receiver

The [I design](INDIRECT_CACHE_STUDY.md) uses one indirect jump site for prelude, real/fixed training and probe. Two distinct targets load separate data lines and return distinct architectural values. After training, the runner sets the architecturally selected target, flushes both data lines **and the pointer slot**, invokes the site once, and times reloading the line for the **other** target. The 12 real/fixed/sham train-label × architectural-target conditions, four hot/cold controls, two fixed-training no-probe controls and four real-training train-matched no-probe controls give 22 conditions per block. There are 22 warm-up and 220 recorded complete blocks, 64 episodes per condition and ten position-balanced 22-block cycles. Calibrate the hit threshold using the first half's hot/cold controls, then check hot/cold and both no-probe families on the held-out half; retain both architectural-target outcomes and the real-minus-fixed and real-minus-sham comparisons. Its unit is cache reload TSC ticks with a calibrated hit classification, **not** H's whole-indirect-probe latency. A positive opposite-target hit association alone cannot prove speculative fetch or execution: verify the exact linked PE, addresses, target exclusivity, absence of architectural opposite-line access and control sensitivity on independent physical sessions before drawing a conditional transient interpretation. This remains a same-process user-mode test.

## L: branch-history prelude sweep

The [L protocol](PRELUDE_SWEEP_STUDY.md) asks whether the previously standardized branch activity changes a fixed short training/probing association. It varies prelude length 128 or 256 and pattern among balanced 0011 (period 4), balanced 16-zero/16-one (period 32), constant zero and constant one, then fixes the immediately preceding all-equal training phase at 32 calls and measures one same-site probe. Real and fixed same-site trainer arms, separate sham and fast/small/PAUSE timer conditions yield 108 cells; 108 warm-up and 864 recorded complete blocks at 32 episodes/cell give eight position-balanced 108-block cycles. The preregistered anchor is the period-32-minus-period-4 difference of real-minus-fixed mismatch contrasts at length 128, separately for probe zero and one. Secondary length and constant-pattern comparisons retain the individual arm components. Prelude transitions, immediate history, timer path and live data handling may all affect timing; no contrast directly measures PHR size or guarantees a predictor reset.

## Paper matrix and a gated branch-presence question

The [claim matrix](PAPER_CLAIM_MATRIX.md) enumerates every reported M1 evaluation category. This package prepares only same-process x86 analogues with different observation endpoints; there is no M1 performance/efficiency core comparison, privilege transition or ASID intervention. A target-specific instruction-cache receiver and an enhanced conditional cache receiver are not implemented in this version. [Phantom branch replacement](PHANTOM_FEASIBILITY.md) is a gated protocol proposal, **not** a batch study. A NOP at a second address does not test the paper's same-site question, and Windows code patching changes cache and branch history. It requires a validated target-only instruction-cache receiver and a matched branch-retention patch positive control before a branch-removed result can be interpreted.

## Shared analysis, controls and provenance

1. Select and print an independent nonzero seed **before** each build and run. Each run must have a complete position-balanced schedule and a verifiable trace with raw condition totals, block/position/condition labels, architectural output checksums, CPU signature, affinity, hypervisor bit, Windows build, timestamps, exact EXE SHA-256 and schedule hash. Record Git HEAD/dirty status, exact `cl`/`ml64`/linker versions and flags, and source/analyzer hashes. Archive even inconclusive or failed attempts.
2. Check the **physical optimized Windows EXEs**, not just source, for the intended branch bytes, shared call sites, runtime decision selection, timed fences and separate timer wrappers. Relocations/ASLR require comparing trace addresses with PE RVAs. The [first pilot audit](results/2026-10-31-windows-suite-pilot/README.md) reviewed the linked PE topology, with residual runtime-clone and alternative-path limitations stated there. Linux source-level tests cannot substitute for a physical instruction audit after any code change.
3. Form paired condition differences **inside each complete block**. The B2/C/D/E/F/H/L timing analyzers apply their declared trimmed estimates and resample complete position cycles for within-run 95% intervals; I calibrates a hit threshold on the first half of each receiver's hot/cold data, checks architectural controls on the held-out half, and reports paired within-block hit-rate contrasts. Report controls, exact samples and all planned outcomes. Within-run intervals do not represent machine-to-machine or day-to-day uncertainty. C reports ticks/iteration; B2/D/E/F/H/L report ticks per probe episode; I reports raw cache reload ticks and hit rates. Cache and speculation-receiver baselines have different endpoints. Never pool these as one effect size.
4. Timer controls show that the specific added work is detectable under their respective wrappers. A large `PAUSE` effect alone does not certify sensitivity to a 2-tick primary contrast. For B2 and D, an audited small-work control has a positive interval lower bound, an upper bound below +8 ticks per probe and a point estimate between +1 and +8, in each tested outcome/length or endpoint context. The coarse `PAUSE` control needs at least 95% positive paired blocks and a positive interval lower bound. E/F/H/L have their own declared small-work and fixed-trainer gates. E additionally tests dose zero; F additionally checks byte-identical copied branch templates and actual virtual addresses. I's held-out receiver gate requires each target's hot hit rate at least 95% and cold and no-probe hit rates at most 5%; this is a measurement-quality gate, **not** a transient-execution gate. For C, fixed-decision and branchless pattern controls and the separate timer must be inspected against its analyzer's declared tolerances. A failed control narrows interpretation rather than justifying deletion of the trace.
5. The [complete pilot](results/2026-10-31-windows-suite-pilot/README.md) ran six baselines and all eight exploratory studies, with a host snapshot and paired timestamped EXE/log per study. Its ZIP integrity, trace replay, disassembly and controls were reviewed, especially the target loads in I. Ten script checks accepted and four remained inconclusive; the pilot is **not** a replication. The [focused follow-up](FOLLOWUP_2026_10_31.md) selects a new primary after seeing that pilot, uses separate sessions/dates and keeps the original A/B archive distinct.

No bootable operating system, custom driver, kernel mode or hardware profiler is required to run this suite. The scientific deliverable is a complete, reproducible local x86 characterization with explicit limitations, not an assertion that these programs reproduce Fractal's Apple M1 privilege-boundary result.

## One VS Code pilot task

To reproduce the full pilot from the **existing repository**, choose **Terminal → Run Task → Complete Windows research pilot (all studies)**. The task takes one host snapshot, reruns cache controls, the existing speculative-cache-receiver check, seeded balanced branch batch, single-branch latency diagnostic, A and B1, then builds, runs and strictly analyzes B2, C, D, E, F, H, I and L with independent seeds in a preselected order. The branch latency script uses its own fixed seed and accepts no run seed; the runner preselects and records seeds for the seeded baselines and eight exploratory studies. `scripts/run_suite_windows.ps1` writes its planned order and every run's status to a timestamped `out/suite-*/session.json`, with a transcript, trace and matching EXE for each completed study. A failed build, run or strict check is recorded and the independent planned studies continue; the suite returns a nonzero status at the end if any study did not pass. Keep every session entry and error transcript for review. Do not label a failed-control study as a validated effect. The 31 October pilot returned nonzero because B2/E/H/L failed gates despite complete traces.

Run **Terminal → Run Task → Exploratory suite: package latest evidence ZIP (Windows)** after a session. This creates one `out/suite-evidence-*.zip` with the session record, host snapshot, all available timestamped trace/EXE pairs, build provenance, disassemblies, and transcripts, including failed attempts. Review the host snapshot for hardware details before sharing the ZIP. The [pilot audit](results/2026-10-31-windows-suite-pilot/README.md) documents the physical review and unresolved apparatus gates; use the separately frozen [Focus protocol](FOLLOWUP_2026_10_31.md) for the selected independent follow-up.
