# Native Windows branch research program and scope boundary

**Scope:** AMD Ryzen 7 9800X3D workstation, native x86-64 programs launched from the existing VS Code repository, one ordinary Windows user-mode security context. This is a staged investigation motivated by the [Fractal paper](https://people.csail.mit.edu/mengjia/data/2026.SP.fractal.pdf), especially its progression from a controlled single-threaded train/receiver test to comparisons between tasks and security domains. It does not run Fractal. The paper's evaluation used Apple M1, separate instruction- and data-cache receivers, and controlled address-space and privilege arrangements. This repository measures x86 timing and prepares one candidate same-domain indirect data-cache receiver under a general-purpose OS. The difference in endpoints and platforms is part of every interpretation. The [claim matrix](PAPER_CLAIM_MATRIX.md) maps all published evaluation cells to this boundary.

| **0. Validate the instrument** | Are architectural hot/cold controls distinguishable, do timer gates detect known extra work, and are the executable bytes and timing units recorded? | Six session baselines: cache controls, existing speculative-cache-receiver check, balanced branch batch, single-branch latency diagnostic, A decision source and B1 history probe; Windows host snapshot; physical pilot executable audits; raw traces and SHA-256 manifests. The earlier single-branch latency trace showed a 47-TSC-tick lattice of unknown cause and lacked a small-work sensitivity gate. | Controls pass at the **scale of the proposed effect** and the optimized binary has the intended branch, call sites and timed region. A large `PAUSE` effect alone cannot validate few-tick sensitivity. The baseline cache receiver and its architectural checks do not validate transient activity; the quantized latency diagnostic cannot establish a prediction null. |
| **1. C must show all pattern contrasts and corresponding fixed/branchless controls, with physical instruction identity checked. This does not count mispredictions or identify predictor capacity. |
| **2. Train, then probe the same branch** | Does a prior decision sequence affect a fixed receiver outcome, and do probe length, intervening activity, training exposure or the standardized prelude change the association? | Archived B1; B2 one versus sixteen calls and same-site fixed trainer; D moves balanced filler around training; E varies the immediately preceding all-equal suffix within a fixed 256-call budget. A signal at one outcome is not a bidirectional crossover. Filler, dose and prelude changes cannot by themselves reveal a hardware history-register length or prove a predictor reset. |
| **3. Vary instruction location under control** | Does the training/probe contrast depend on which **audited virtual branch site and call path** is used? | F supplies a within-process comparison of three byte-verified cloned sites and a common receiver. A broader address sweep is excluded from this version; F's physical address/EXE audit and first run are pending. | Record actual function addresses, instruction bytes, call paths, same-site controls and layout across variants. The complete path differs, so a contrast indicates sensitivity to this layout, not an aliasing table size, individual index bit or specific predictor structure. |
| **4. Separate sender and receiver execution** | Can a same-process user-mode sender and receiver be handed control reproducibly at one branch site? | G was assessed for feasibility and **excluded from the current suite**: ordinary Windows thread handoff leaves scheduler activity and precise same-core timing insufficiently controlled for the proposed contrast. No G source or physical result is claimed. | Reconsider only after an apparatus can verify affinity and handoff, run a complete sham/context-switch control, keep handoff outside timing and audit the physical executable. Even a repeatable same-process effect would not test ASID or user/kernel isolation. |
| **5. Distinguish timing from speculative activity** | Is an architecturally unselected target's data line measurably affected by a prior branch target? | Earlier conditional cache probes yielded a null host trace with architectural controls. [H](INDIRECT_TARGET_STUDY.md) is an indirect-target whole-probe timing baseline. [I](INDIRECT_CACHE_STUDY.md) adds a candidate indirect target-specific data-cache receiver; its first physical run, controls and linked-PE audit are pending. A target-specific instruction-cache receiver and an enhanced conditional cache receiver are **not implemented** in this version. [Phantom branch replacement](PHANTOM_FEASIBILITY.md) remains gated by a validated fetch receiver and patch-survival positive control. | Calibrate the receiver with held-out hot/cold and train-matched no-probe controls, verify target-exclusive loads and absence of architectural opposite-line access in the linked PE, retain both outcomes and repeat independent sessions. H's whole-call timing cannot isolate speculative fetch; a data-cache association alone cannot prove transient execution or cross-domain behavior. |
| **6. Cross a protected domain** | Can training in one privilege level or address space influence a receiver in another while all other variables remain controlled? | **Outside this Windows user-mode package.** Ordinary processes change address space, scheduler history, code layout and potentially mitigations. Running two user processes does not itself isolate ASID as a variable. User/kernel sharing needs controlled kernel execution or a research OS/driver; M1-specific p/e-core and CSV2 results require Apple hardware. | Only an independently designed apparatus with verified domain transition, mirrored code/layout where required, working same-domain positive controls and a receiver with proven sensitivity could support such a claim. No USB boot or kernel change is required for the completed native studies. |
| **7. Replicate and report** | Is a chosen, control-supported effect stable beyond a pilot run? | Original batch and A/B archives; the new session runs six baselines and B2/C/D/E/F/H/I/L, recording seeds for seeded runs, software hashes, host state, physical EXE/log pairs and failed attempts. The follow-up supports one to eight rounds; eight rotate all eight exploratory studies through each study position. | Freeze one primary comparison **after the exploratory pilot**, run unchanged code on separate dates, keep runs as the replication units, and report day/order/host limitations. Within-run cycle bootstrap intervals cannot substitute for uncertainty across independent days or machines. |

## Decisions after the first new suite session

1. **Build or trace failure:** preserve the executable, log and transcript. Correct the implementation as a new version before another physical run. Do not count a failed attempt as a null result or silently replace it.
2. **Binary layout or small-control failure:** retain the data as an engineering pilot. Audit the physical instruction sequence and timer scale, then version a corrected protocol. No mechanism claim follows from a failed control.
3. **Valid controls, null primary contrasts:** publish the null estimates with uncertainty and exact conditions. Select a new hypothesis only if it addresses a documented limitation, and label it exploratory.
4. **Valid controls, stable exploratory contrast:** compare both outcomes and controls, select one falsifiable primary estimand in a new frozen protocol, and repeat unchanged on distinct dates. Cross-study timings have different units and different branch addresses, so do not pool them as one effect size.
5. **After independent replication:** write a claim ledger separating directly observed latencies from inferred hardware explanations. A scientifically useful result can be a reproducible bounded timing characterization even when it does not reveal the exact predictor circuit.

The [full-session guide](WINDOWS_MULTI_EXPERIMENT_SUITE.md) describes the pilot VS Code task, eight exploratory studies and follow-up rotation. The [paper claim matrix](PAPER_CLAIM_MATRIX.md) distinguishes this bounded x86 same-process program from the authors' 48 M1 evaluation cells. G, an expanded address sweep, separate fetch and conditional cache receivers, and a same-site Phantom assay are excluded from the executable suite for stated measurement or environment reasons. Stage 6 is a different system-software and hardware research program, not an unfinished VS Code task that can be completed by increasing sample counts. No amount of these user-mode data alone establishes Fractal's M1 privilege-boundary result.
