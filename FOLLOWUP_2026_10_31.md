# Focused Windows x86 follow-up after the 31 October pilot

**Protocol status:** written after inspection of the first complete Windows
suite pilot. Its hypotheses were selected with knowledge of that pilot and are
therefore **new follow-up hypotheses**, not prospective tests of the pilot
itself. The pilot is excluded from all follow-up replication counts. Read-only
inspection of the supplied pilot's linked PE found A's conditional branch at
RVA `0x1bf0`, branchless `cmovne` decision selection and one direct feeder
call at RVA `0x1a8a`; its `.text` hash matched the previously audited A
pilot. C's primary arms used a common branch at RVA `0x2080`, with its
branchless control at RVA `0x2099`. No A/C primary-path blocker was found.
This verifies the observed instruction layout, not a predictor mechanism.
Secondary B2, F and I interpretation remains conditional on their own physical
path audits. Any later audit blocker pauses the affected interpretation until
a versioned correction is reviewed.

The source of the pilot is Git `8209c42`; its supplied evidence archive is
`suite-evidence-suite-20261031T213948Z-8ee83ab7.zip` (SHA-256
`e595d4fb38638961d4c9a2a8eb0ee1f25789b2899cb668a02989d4ec5e2ba40e`).

## Frozen endpoints and controls

### Primary: C's shuffled versus period-32 decision stream

Within each complete C block, let `Y(mode, pattern)` be the timed total of
8,192 calls. Use the existing analyzer's 10% trimmed mean of the **blockwise**
adjusted contrast, divided by 8,192:

```text
C_new = [(Y(live, shuffle) - Y(live, p32))
         - (Y(fixed, shuffle) - Y(fixed, p32))] / 8192
```

The new directional hypothesis is `C_new > 0` under this executable and
host protocol. Report a two-sided within-run 95% whole-cycle bootstrap interval
and every run estimate regardless of sign. For the new comparison, the *full*
fixed-mode and branchless shuffled-minus-`p32` intervals must each fit
inside the previously declared ±0.5 tick/iteration practical margin. Its
added-work timer must have a positive interval lower bound and be positive in
at least 95% of complete blocks. Preserve C's **original** period-2-minus-
period-32 primary, its original controls, all other periodic comparisons, and
the adjusted shuffle-minus-`p4` anchor. The new primary was selected after
the pilot; its pilot estimate is never pooled with the follow-up estimates.
Period and shuffled streams also differ in transition distribution, so this
cannot isolate an entropy mechanism or predictor capacity.

### Reference: A's unchanged decision-order protocol

Report A's original within-block interaction and all three original
±0.5-tick/iteration practical negative controls. Require the original added-
work timer gate: at least 95% positive paired blocks and a positive within-run
interval lower bound. A is a separate executable and estimand. Its magnitude
must not be pooled with C merely because both are in ticks/iteration. Historical
A runs remain context, not part of these six new session estimates.

### Exploratory and secondary outcomes

Report B2's four `F(p,n)=D_real(p,n)-D_fixed(p,n)` outcomes, both paired length
interactions, all sham comparisons, and **all four** originally required
small-work, PAUSE and fixed-neutral controls. The hypothesis that `F(0,1)`
recurs is a pilot-informed candidate, not a second confirmatory primary.
If probe-1's small-work gate fails again, keep the run and label B2
inconclusive under its original protocol, even if the probe-0 interval is
positive. Do not reinterpret the pilot's failing B2 as a successful study.

D retains both probe outcomes and all four filler positions; F retains both
probe outcomes, all three trainer sites and its byte/address checks; I retains
both target directions, calibrated hit thresholds and held-out hot/cold and
train-matched no-call controls. Report their existing paired estimands and
within-run intervals, with no selected positive endpoint treated as a new
primary. A timer or receiver passing its control is a measurement-quality
result, not a hardware-mechanism finding. Do not use D/F/I confidence intervals
that merely include zero to assert equivalence or the absence of hardware
behavior.

## Collection plan

With the A/C pilot primary paths audited, run **six separate Focus sessions**,
three on each of two distinct **UTC dates**. This exceeds the minimum of three
sessions across two dates while retaining only two date-level clusters. Start
a fresh invocation for every session. The Focus plan includes four baselines (cache controls,
branch batch, A and B1) and five exploratory studies (C, B2, D, F and I).
The suite preselects independent nonzero seeds, records a new host snapshot,
randomizes exploratory study order, and archives failures as well as successes.
Do not rerun a failed-control session as a replacement; an additional run is
an explicitly numbered additional attempt.

From the repository root in Windows PowerShell, run one session with:

```powershell
./scripts/run_suite_windows.ps1 -Phase Followup -StudySet Focus -Rounds 1
```

The VS Code task **Focused Windows follow-up session** runs the same command.
After *each* invocation, package that exact session using
`./scripts/package_suite_windows.ps1` before starting another. Keep the
resulting distinct evidence ZIPs, including those from sessions that return a
nonzero status. Focus accepts exactly one round per invocation. Eight Full-suite
rounds in one process are not a substitute for separate dates because their
measurements remain correlated.

After collection, pass the **six exact follow-up evidence ZIP paths** to
`scripts/summarize_suite_followup.py` with `--output` for a reproducible JSON
attempt ledger and descriptive A/C summary. Do not include either pilot ZIP
in that invocation. The summary is an analysis aid; inspect all C controls
for the **new** shuffled-versus-`p32` comparison as well as the original C
controls before applying this protocol's replication criterion.

Freeze the study C/ASM, analyzers, compiler flags and tool versions for all
six sessions. Capture the Git HEAD, dirty status, source hashes, individual
EXE and `.text` hashes, actual branch addresses/affinity, UTC starts,
Windows build, hypervisor status, and available host configuration. Avoid
known workload changes when possible; record any that happen. If an
implementation correction is necessary, retain the affected attempts and
start a new protocol version rather than mixing revisions. The protocol and
any code added solely for orchestration or summaries must be hashed in each
session plan.

## Analysis and reporting rule

First verify archive integrity, original trace replay, checksums, seeds,
EXE/trace hashes, linked instructions, and every declared per-run control.
The unit of repeated observation is the **complete session run**, not its
randomized blocks or 8,192 iterations. Report a ledger of all six planned
sessions and any extra attempts, including build errors, control failures and
null/reversed estimates. Do not select only passing or positive runs when
describing the attempt set. Label a run eligible for a control-supported C
estimate only if its original C gates **and** the new comparison's fixed,
branchless and timer gates pass; show ineligible estimates separately.

For eligible C and A runs, show every run-level estimate with its within-run
interval, each date's median and range, and the overall range. Compare
signs and magnitudes across dates descriptively. The predeclared descriptive
replication criterion for C is **six eligible C runs, all six positive point
estimates with positive within-run interval lower bounds, and positive date
medians on both dates**. Meeting it supports a reproducible same-host
decision-order timing association under this protocol. It is not a formal
population-level test: with only two dates, do not present a narrow within-run
interval as between-day certainty or claim population-wide Ryzen behavior.
A failed gate, mixed signs or material date shift limits the conclusion and
must be reported, without replacing a failed attempt.
The original C period-2 contrast and B2/D/F/I outcomes are reported alongside
the new primary without promoting whichever is most favorable afterward.

These are ordinary Windows user-mode x86 measurements. Neither positive nor
null timing, an I data-cache association, or this follow-up's sample count
can prove Fractal's Apple M1 p/e-core, ASID, cross-privilege or Phantom results,
identify a predictor table, count mispredictions, or validate Fractal OS's
multi-privilege scheduler. See [PAPER_CLAIM_MATRIX.md](PAPER_CLAIM_MATRIX.md)
for the claim-by-claim boundary.
