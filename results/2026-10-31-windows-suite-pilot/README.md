# Windows exploratory suite pilot, 31 October 2026

**Status:** One native Windows user-mode pilot on one AMD Ryzen 7 9800X3D host. All 14 planned studies built and produced trace/EXE pairs. Ten passed their script's current trace and control checks; four were retained as **inconclusive** because declared controls failed. This is an apparatus and exploratory-results audit, not a confirmation series or a replication of Fractal's Apple M1 and protected-domain findings.

The disassemblies show the intended high-level instruction topology for these pilots. The evidence does not include hardware event counts or a direct proof that a particular timing contrast was caused by a predictor misprediction. Ordinary Windows scheduling and the reported hypervisor can alter the history and measurement noise. A source/EXE hash pairing is a traceability check, not an independent attestation of all host conditions.

## Claim boundary and next decision

The strongest existing result remains a repeatable **same-host conditional decision-order timing association**, now with another controlled Study A observation. C adds an exploratory comparison in which fresh balanced shuffles differ markedly from periodic sequences, while the tested periodic run lengths are similar. D does not show a clear filler-position effect; F's planned site interaction is uncertain; I's receiver passes architectural calibration yet shows no convincing opposite-target data-cache effect. These statements describe the specific optimized executables and tested host, not all Ryzen processors.

The paper's Apple M1 experiments use target-specific instruction-cache fetch and data-cache execution receivers, then vary privilege and ASID under Fractal's scheduler. This native Windows suite measures mostly TSC timing within one ordinary user-mode process and has no protected-domain intervention. It does **not** confirm or refute Fractal's M1 predictor isolation or Phantom observations, prove transient execution, count mispredictions, identify a predictor table size or evaluate Fractal OS noise claims. The [paper claim matrix](../../PAPER_CLAIM_MATRIX.md) retains those boundaries.

Before a follow-up: preserve this archive unchanged, freeze a small number of hypotheses as a **new protocol**, audit the F runtime copies if address results will be used, and resolve L/E/H/B2 sensitivity/equivalence failures with versioned changes and a fresh pilot. Repeating failed-control runs or relaxing a gate after observing these data is not confirmation. Run-level repetition on separate dates, complete source/binary provenance and both probe directions are required for stronger same-host evidence; within-run blocks cannot be counted as independent sessions.
